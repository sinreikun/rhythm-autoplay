# 音ゲー汎用外部オートプレイプログラム 設計書 v0.2

作成: 2026-11-06 / 改訂: 2026-11-06（対象タイトル・言語・配布方式を確定） / 対象: Windows PC 上の音ゲー（スマホ画面のミラーリング表示も含む）

## 0. 結論

- 汎用化の鍵は「検出器の汎用化」ではなく、**共通コア（時計・予測・スケジューラ・入力）の汎用化＋ゲーム別プロファイル＋形状ファミリ別検出器**に分けることです。1つの検出器で全音ゲーは追えません。
- 方式は**反応型ではなく予測型**が必須です。ノーツが判定ラインに「来てから押す」のではキャプチャ遅延のばらつき（ジッタ）がそのまま判定に乗ります。ノーツを追跡して到達時刻 `t_hit` を推定し、未来の入力キューに予約して、高分解能タイマで発火します。
- 精度を決めるのは遅延の絶対値ではなく**ジッタ**です。遅延はオフセット補正で消せますが、ばらつきは消せません。目標: パイプライン全体のジッタ σ < 3 ms、判定ウィンドウの 1/10 以下。

## 1. 前提・非対象

### 前提（外部方式の定義）
- 入力情報は **画面キャプチャと音声のみ**。プロセスメモリ読み、譜面ファイル解析、内部変数参照は主経路にしません（SelfStruct / Game攻略くん と同じ外部観測の原則です）。
- 出力は OS / ハードウェア経由の通常入力（キーボード・マウス・タッチ）だけです。
- ゲーム側の改造・注入はしません。

### 非対象（v1）
- 判定が音声波形そのものへの追従を要求するタイプ（歌唱・楽器系）。
- ノーツがワープ・消失・再出現する演出型ギミックの完全対応（§10 の制限を参照）。

## 2. 形状ファミリ（検出器の分類）

汎用性はこの3分類で確保します。新規ゲームは「どのファミリか＋プロファイル」で追加でき、コアは触りません。

| ファミリ | 代表形 | 検出方法 | 入力 |
|---|---|---|---|
| A: レーン落下型 | 縦/横スクロール、固定レーン数可変 | レーン ROI の透視補正 → 色/テンプレート検出 → 軌跡追跡 | キー down/up |
| B: 自由位置型 | 画面上の任意位置に出現する円・ターゲット | 全画面検出（色/円/テンプレート、任意で軽量 ML）→ 出現位置と時刻 | マウス移動＋クリック / タッチ |
| C: 放射・回転型 | 円形レーン、回転する判定点 | 極座標変換して A 型に帰着 | キー down/up |

まず A を作り、C は A の前処理として吸収、B は別検出器として追加する順序が現実的です。

## 3. 全体構成

```
[Capture]        DXGI Desktop Duplication / Windows Graphics Capture
  │  frame + QPC timestamp（GPU テクスチャ、ゼロコピー寄り）
  ▼
[Preprocess]     ROI 切り出し・透視補正・色空間変換（ファミリ別）
  ▼
[Detect]         ノーツ候補検出（古典 CV 中心、ML は任意の補助）
  ▼
[Track/Predict]  トラック ID 付与 → 速度推定 → t_hit 推定（§5）
  ▼
[Scheduler]      t_hit 順の優先度キュー → 高分解能発火（§6）
  ▼
[Input]          SendInput / 仮想 HID / 実 HID（§7、差し替え可能）
  ▲
[Feedback]       判定表示（Perfect/Great 等）の OCR/色検出 → オフセット自動補正（§8）
[Profile]        ゲーム別定義（§4）。全段が参照する
[Clock]          QPC を唯一のマスタークロックとし、全 timestamp をこれに統一
```

スレッド分離: Capture / Detect / Schedule+Input の3スレッド。ホットループ内ではアロケーションと GC を避けます。UI・プロファイル編集は別プロセス/別スレッドに隔離し、ホットループに触れさせません。

## 4. ゲーム別プロファイル（コードではなくデータ）

```yaml
game: example-game
family: lane_fall            # lane_fall | free_field | radial
window: { match: "Example Game", capture: borderless }
geometry:
  scroll: down               # down|up|left|right
  judgment_line_y: 0.86      # ROI 内の相対位置
  lanes:
    - { id: 0, x_center: 0.20, width: 0.13, key: D }
    - { id: 1, x_center: 0.40, width: 0.13, key: F }
    - { id: 2, x_center: 0.60, width: 0.13, key: J }
    - { id: 3, x_center: 0.80, width: 0.13, key: K }
notes:
  tap:   { color_hsv: [95, 120, 120], shape: rect }
  hold:  { color_hsv: [45, 120, 120], tail_tracking: true }
  flick: { color_hsv: [0, 0, 200], marker: arrow }
timing:
  offset_ms: 0               # キャリブレーションで自動上書き
  assume_constant_scroll: true
feedback:
  judgment_roi: [0.42, 0.55, 0.16, 0.08]   # 判定文字の出現領域
```

プロファイル作成支援（ウィザード）が汎用性の実体です:
1. ウィンドウを選ぶ → 2. 判定ラインとレーンをドラッグで置く → 3. ノーツ色をスポイトで拾う → 4. テストプレイ録画で検出漏れを目視確認 → 5. 自動キャリブレーション（§8）。

手作業で YAML を書かせる設計にすると、汎用でも誰も2本目を追加しません。

## 5. 追跡と到達時刻の予測

- 検出点にトラック ID を付け、同一ノーツの位置系列 `{(t_i, y_i)}` を保持します。
- 直近 N 点に最小二乗（等速前提）または Kalman フィルタを当て、`y = judgment_line` となる時刻を `t_hit` として推定し、フレームごとに更新します。
- 信頼条件: トラック長 ≥ 3 点、推定残差が閾値内、の両方を満たした時点で初めてスケジューラへ登録します。満たさないノーツは捨てるのではなく「未確定」として保持し続けます。
- 変速（ソフラン）対策: 残差が系統的に増えたら区間線形に切り替え、直近の短い窓だけで再推定します。停止ギミックは「速度 0 の区間」として同じ枠で扱えますが、停止後の再加速点は予測できないため、その区間だけ反応型にフォールバックします（精度は落ちることを明示します）。

### ノーツ種別の状態機械
- **Tap**: `t_hit` に down、固定 30–50 ms 後に up。
- **Hold**: `t_hit` に down、尾の追跡が終わる時刻（尾端のライン通過）に up。途中で尾を見失ったら安全側として少し長めに保持します。
- **同時押し**: `t_hit` 差が 5 ms 以内は同一グループとして同一発火バッチにまとめます（1件ずつ発火すると後発が遅れます）。
- **Flick / スライド**: 方向ベクトル付きの入力シーケンス（down → 移動 → up）を1イベントとして予約します。

## 6. スケジューラと時計

- マスタークロックは QPC のみ。キャプチャ timestamp、音声 timestamp、入力発火はすべて QPC に換算してから比較します（混ぜると必ずずれます）。
- 予約キューは `t_hit` 昇順。発火スレッドは「次の発火まで sleep（高分解能 waitable timer）→ 最後の 1–2 ms だけビジーウェイト」で待機し、スレッド優先度は最高、コア固定寄りで運用します。
- 遅れの扱い: 発火遅延が 10 ms を超えたイベントは「遅延あり」として記録し、統計に出します。黙って流すと精度劣化に気づけません。

### 遅延予算（目標値、実測で置き換える）
| 段 | 遅延 | ジッタ目標 |
|---|---|---|
| キャプチャ（120–240 fps） | 4–8 ms | < 2 ms |
| 前処理＋検出 | 1–3 ms | < 1 ms |
| 追跡＋予測 | < 0.5 ms | — |
| スケジューラ発火 | 補正で相殺 | < 1 ms |
| 入力（SendInput→ゲーム） | 1–5 ms | < 2 ms |

絶対遅延の合計はオフセットで相殺されるため、合算値より各段のジッタ合計が品質指標です。

## 7. 入力バックエンド（差し替え式、3段）

| 段 | 方式 | 特徴 |
|---|---|---|
| 1 | `SendInput` | 実装が最速・最簡単。一部ゲームは注入入力を無視/検出します。まずこれで作ります |
| 2 | 仮想 HID ドライバ | ドライバ署名と配布の手間が増えますが、OS からは通常デバイスに見えます |
| 3 | 実 HID（Arduino Leonardo 等のマイコンを USB キーボード/マウスとして使う） | 最も「外部」寄りで汎用性が高い反面、配線とファーム書き込みが必要です。スマホ実機タッチは静電容量式スタイラス駆動など物理層の話になるため別プロジェクト扱いです |

注意: オンライン対戦・ランキングのあるタイトルでは、注入検出や利用規約の問題が方式ではなくタイトルごとに発生します。オフライン/練習モードでの検証を前提に設計し、対象可否はプロファイル側のメモ欄で管理します。

## 8. キャリブレーションと閉ループ補正

1. **静的測定**: 既知時刻に点滅する自作テスト画面＋入力エコーで、キャプチャ→入力の往復遅延とジッタを実測します（推測でオフセットを置きません）。
2. **ゲーム内初期合わせ**: ゲーム側の判定調整機能がある場合はそちらを正とし、本プログラム側 offset は 0 を基準にします。二重補正が一番あるミスです。
3. **閉ループ**: 判定表示（Perfect/Great/Good の色・文字）を読み、EARLY/LATE の偏りを集計して offset を 1 ms 単位で自動追従させます。これが無いと、曲やシーンごとの負荷変動で静かにずれ続けます。

## 9. 学習ラン（2周目方式）

初見で追えないギミック譜面向けの補助モードです。
- 1周目: 観測専用でプレイを録画し、`t_hit` 列（譜面マップ）を構築します（入力はしません/下手にしません）。
- 2周目: 譜面マップを正として再生し、映像は「再生位置の照合」と「マップに無いノーツの検出」だけに使います。
汎用外部方式のまま精度上限を上げる現実的な逃げ道として、最初から仕様に入れておきます。

## 10. 制限（先に明示する）

- エフェクトでノーツが隠れる/色が変わる演出、ワープ系ギミックは検出が原理的に破れます。プロファイルで「その曲は対象外」と切れることが仕様です。
- 排他フルスクリーンやキャプチャ不可（黒画面）のタイトルは、ボーダーレス化できない時点で対象外です。
- 判定ウィンドウが ±10 ms 級のタイトルでは、仮想 HID 段と高リフレッシュレートキャプチャが事実上必須になります。

## 11. 実装スタック案

- **製品**: C# (.NET 8) + DXGI/WGC キャプチャ + OpenCvSharp。開発速度と Windows 親和性を優先し、ホットループだけ必要なら C++ に切り出せる構造にします。
- **試作**: Python + dxcam + OpenCV で検出・予測の正しさを先に検証します。ただし Python はジッタ 10–20 ms 級になりがちで「最高難度で戦えるか」の判定には使えません。試作の合格条件は検出率と `t_hit` 推定誤差（オフライン録画に対する誤差）で定義します。
- **検証ハーネス**: 既知の `t_hit` を持つ自作の簡易音ゲー（テスト画面）を先に作ります。これが無いと、実ゲームでの失敗が「検出・予測・遅延」のどれか切り分けられません。

## 12. 開発フェーズと合格条件

| Phase | 内容 | 合格条件 |
|---|---|---|
| 0 | 検証ハーネス＋遅延実測 | 往復ジッタの実測値が記録できる |
| 1 | A型・Tap のみ、予測＋スケジューラ＋SendInput | ハーネス上で判定ウィンドウ内 99% / 実ゲーム1タイトルでフルコンボ級 |
| 2 | Hold・同時押し・Flick、閉ループ補正 | EARLY/LATE 偏りが自動で ±3 ms 内に収束 |
| 3 | プロファイルウィザード、C型（極座標） | コード変更なしに新規タイトルを1本追加できる |
| 4 | 学習ラン、B型（自由位置） | ギミック譜面と自由位置型を各1タイトル |

## 13. 決定事項（2026-11-06、マスター指示）

1. **最初の対象タイトル: Steam 版 HYPNOSYNC**（App ID 2986590、無料、2026-10-30 リリース、BASED KICK）。詳細は §14。
2. **言語: C# (.NET 8)**（サキに委任され決定）。理由: Windows キャプチャ（DXGI/WGC）・SendInput・OpenCvSharp の実績が厚く、開発速度と遅延要件を両立できるためです。試作を Python で挟む案は、移植コストとジッタ検証の二度手間を避けるため採りません。
3. **公開・運用: GitHub 公開リポジトリ `sinreikun/rhythm-autoplay`**。改修ごとに `version.txt` の版を上げて push し、GitHub Actions が自動でテスト・ビルド・Release 公開まで行います（§15）。
4. **配布方式: ユーザーに配るのは軽量な起動用 exe（ランチャー）のみ**。ランチャーは起動のたびに GitHub の最新版を確認し、本体を自動更新します（§15）。ランチャー自体は Native AOT で単体動作させ、.NET ランタイムの事前導入を不要にします。

## 14. HYPNOSYNC 固有仕様（調査済み 2026-11-06）

出典: Steam 公式 API・ストア本文、電ファミニコゲーマー／AUTOMATON の紹介記事、Steam コミュニティのレビューとキー配置ガイド。実機の画面での最終確認は v0.2 の実機検証で行います。

- **形状**: 4レーンの縦スクロール（奥から手前への台形・透視投影レーン）。判定は下端の「ブレイクライン」。透視補正で矩形化すれば A 型（レーン落下型）の検出器がそのまま使えます。
- **ノーツは色で種類が決まり、全色が同じ4レーンに現れます**（公式: 意志力は色で区別され5種類すべてが同じレーンに現れる）。
  - 赤ノーツ → そのレーンの「赤キー」
  - 青ノーツ → そのレーンの「青キー」（赤とは別キー。合計 8 キー）
  - 紫ノーツ → 赤＋青の同時押し
  - 黄ノーツ → 赤・青どちらでも可
  - 横長ノーツ（矢印付き）→ レバー/方向入力（上下左右の4キー）
- **合計 12 キー**を使う設計で、キーボード向けではないとレビューで繰り返し指摘されています（= オートプレイの需要が最も高いタイプです）。キー割り当てはゲーム内設定（Settings → View Keybinds → Edit Keybinds）で変更できます。
- **推奨キー配置（本プログラムのプロファイル既定値、コミュニティで実績のある配置）**: 赤 = D F J K（レーン1–4）、青 = E R U I、方向 = S（左） L（右） V（下） N（上）。ユーザーはゲーム内設定をこの配置に合わせます。
- 判定表示は BASED! / GREAT / OK? / CRINGE。閉ループ補正（§8）の読み取り対象はこの表示とコンボ数です。
- 実行ファイル名は `HYPNOSYNC.exe`（コミュニティのガイド記載）。ウィンドウ特定はこれとタイトルで行います。
- 注意: レビューに「外部ツールでのキーリマップ対策とみられる入力の取りこぼし」の報告があります。SendInput が素直に通るかは v0.2 実機検証の最初の確認項目です。通らない場合は §7 の段2（仮想 HID）へ進みます。

## 15. 配布・自動更新アーキテクチャ

```
配布物: RhythmAutoplay.exe（ランチャー、Native AOT、単体・軽量）
  │ 起動のたびに実行
  ├─ 1. GitHub API で releases/latest の tag を取得
  ├─ 2. %LOCALAPPDATA%\RhythmAutoplay\installed-version.txt と比較
  ├─ 3. 差があれば Body zip を取得し、SHA-256（.sha256 資産）を照合して
  │     versions\<tag>\ へ展開（旧版は残し、失敗時は旧版で起動）
  ├─ 4. RhythmAutoplayBody.exe を起動して終了（引数は素通し）
  └─ オフライン時: 取得に失敗したら導入済みの最新版をそのまま起動
本体: RhythmAutoplay-Body.zip（self-contained 単一ファイル + profiles）
版管理: リポジトリ直下 version.txt が唯一の正。タグは v<version.txt>。
公開: main への push で Actions が test → build → Release 作成まで自動実行。
      同じ版の Release が既にある場合は公開をスキップします（再配布事故防止）。
```

ランチャー自身の更新が必要になるのは更新機構そのものを変える時だけで、その場合も Release 資産として新しいランチャーを置き、README と Release ノートで差し替えを案内します（頻度は設計上ほぼゼロに保ちます）。
